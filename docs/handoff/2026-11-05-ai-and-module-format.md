# 인수인계: AI 기능 정비와 모듈 형식 개편

- 작성일: 2026-11-05
- 출처: `memory_notion` 저장소에서 진행한 노트 체계 점검 세션
- 상태: 6절의 1.2.0 작업과 예전 문서 정리를 `main`에 병합했습니다(2026-11-05). 리뷰(7절)는 수동 시험을 마치고 `main`에 병합했습니다(2026-11-06). 6절 10번(JSON 출력)은 `feature/json-output` 브랜치에 구현했으며(2026-11-06, 8.7절), 병합 전입니다.

> 이 문서와 테스트 데이터에 실제 업무 노트를 넣지 마십시오. `memory_notion`의 타임라인에는 회사 업무 내용이 있습니다. 회귀 테스트는 합성 데이터로 작성합니다.

## 1. 배경

사용자는 `memory_tool`을 개인 노트(`memory_notion/.memory`)에 쓰고 있으며, 체계가 무겁고 모듈화 방법을 정하기 어렵다고 느낍니다. 점검에서 확인한 원인은 다음과 같습니다.

- 도구가 코딩 에이전트의 프로젝트 맥락 관리를 중심으로 설계되어, 개발용 구조가 개인 노트에도 그대로 적용되었습니다.
- 타임라인 기록은 쌓이지만 모듈로 옮기는 절차가 작동하지 않습니다.
- Obsidian 플러그인 패널은 오늘 기록만 보여 줍니다. 태블릿에서는 지난주와 이번 주의 기록을 이어 보기 어려웠습니다.
- 파일명과 모듈 구조를 바꿀 때 AI 코드가 함께 갱신되지 않았고, 이를 잡아 줄 테스트도 없습니다.

## 2. 확정된 결정

1. **도구 경계:** Goal Loop는 사전 계획, Memory Tool은 사후 기록입니다. 타임라인과 AI 상담 화면을 Goal Loop 앱에 넣지 않습니다.
2. **시작 환경:** 노트북과 데스크톱의 VS Code부터 시작합니다. Obsidian에서 전체 AI 지원을 받는 일은 추후 서버 접속 방식으로 검토합니다. 동기화에는 Obsidian Sync를 쓰고 있습니다.
3. **문서 작성:** 사용자와 AI가 모두 씁니다. 사용자는 문해력과 문장력을 유지하기 위해 직접 쓰는 것을 목표로 하고, 어려울 때 AI에게 의지합니다. 따라서 AI 초안을 기본값으로 삼지 않습니다.
4. **OKF:** 전체 규격이 아니라 부분 도입합니다.
5. **`auto-tag`:** 제거합니다.
6. **`ai-organize`, `suggest-ai`:** 아이디어만 참고하여 AI 기능 정비와 함께 처리합니다.
7. **Notion 키:** 사용자에 따르면 이미 폐기된 키이므로 우선순위가 낮습니다. 사용자는 현재 Notion 동기화를 쓰지 않습니다.
8. **주간 리뷰 스킬:** 만들지 않습니다. 리뷰는 `mreview` 하나로 처리합니다(7절).
9. **문서 종류:** 참고, 이해, 방법, 판단의 4종으로 시작합니다. `type`은 선택 항목이며, 도구는 알 수 없는 값도 거부하지 않습니다. 새 문서 20개 정도를 쓴 뒤 둘 사이에서 자주 망설이면 `방법`을 `참고`에 합칩니다.

   | 종류 | 답하는 질문 | 갱신 계기 | 기존 분류 |
   |:---|:---|:---|:---|
   | 참고 | 그 값이나 사실이 무엇이었지? | 대상이 바뀔 때 | `reference`, `implementation`, `tracker`, 진행 중인 `inquiry` |
   | 이해 | 왜 이렇게 작동하지? | 이해가 깊어질 때 | `concept` |
   | 방법 | 어떻게 하지? | 적용하다 실패했을 때 | `method` |
   | 판단 | 왜 그렇게 보았거나 정했지? | 고쳐 쓰지 않고 새 판단으로 대체 | `analysis`, 끝난 `inquiry` |

10. **문서 밖으로 보내는 내용:** 일상 기록과 `idea`, 작은 결정은 타임라인에 남기고, `plan`은 Goal Loop로 보냅니다. 미결 질문은 `참고` 문서의 `## 열린 질문` 제목 아래에 적고, 결론이 나면 `판단` 문서를 만들어 링크합니다.
11. **문서 모양:** 템플릿을 완전히 제거합니다. `mmodule create`는 frontmatter와 제목만 만들며, 필수 절과 안내 주석은 없습니다. 필드는 `type`, `description`, `tags`, `generated`로 시작하고, `sources`와 `stale_after`는 해당될 때만 씁니다.
12. **작성 지원:** 종류별 AI 가이드(질문과 점검 항목)를 두고 `mmodule guide <종류>`와 `mt-write` 스킬로 전달합니다. CLI에 대화 화면을 만들지 않습니다. 임시 기본 동작은 질문, 작성 후 지적, 막힐 때 개요, 요청 시 대신 작성의 순서입니다.
13. **코드 프로젝트:** 문서 종류가 아니라 지식 베이스가 놓인 장소와 코드 연결로 봅니다. `--project`를 만들지 않으며, 코드 연결은 어떤 문서든 `sources`에 적을 수 있습니다. 기존 `Related Files`도 계속 읽습니다.
14. **현황:** 별도의 종류나 문서로 두지 않습니다. 코드 작업을 재개할 때는 타임라인과 Git을 읽고, Goal Loop가 있으면 함께 읽습니다. Goal Loop는 별도의 프로그램이므로 도구와 안내문이 그 존재를 전제하면 안 됩니다. 계속 변하는 상황을 추적하는 문서는 `참고`와 `stale_after`로 처리합니다.
15. **기존 구조:** Kind, Nature, `grow`, `--part`, `--draft`, 번들 템플릿은 호환 기간을 거쳐 제거합니다. 다른 사용자를 위해 쓰기 기능을 경고와 함께 당분간 유지합니다. 제거 시기는 정하지 않았으며, 이후에 제거할 수 있습니다. 기존 문서를 읽는 기능은 제거하지 않습니다.
16. **`PLAN.md`:** `mplan module`과 함께 호환 기간 없이 제거합니다. `mplan`의 나머지 기능과 `PLAN-*.md` 처리는 유지합니다.
17. **하위 문서:** 도구로 하위 문서를 만들면 `topic.md`를 `topic/topic.md`로 옮기고, 하위 문서는 `topic/child.md`로 만듭니다. 상위 문서의 내용은 건드리지 않습니다. 상위 문서가 없는 폴더와, Obsidian에서 직접 만든 `topic.md`, `topic/child.md` 형태도 정상으로 처리합니다.
18. **AI 명령:** `ai-organize`를 `mmodule audit`으로 바꾸고, 이동, 계층, 네임스페이스 제안은 버립니다. 분리와 병합 후보 계산은 리뷰의 입력으로 재사용합니다. `suggest-ai`는 `suggest-links --ai`로 합칩니다. 모든 기능은 제안만 하며, 문서는 승인 후에 바꿉니다.
19. **OKF 방향 수정:** `title`은 파일명과 다를 때만 씁니다. `index.md`는 자동으로 만들지 않고, 있을 때만 읽습니다.

## 4. OKF 부분 도입 방향

참고: [OKF SPEC v0.2](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md)

**가져오는 것:** frontmatter의 `type`, `title`, `description`, `tags`, `generated`, `sources`, `stale_after`와 폴더별 `index.md`

**가져오지 않는 것:** Attested Computation과 관련 필드, 규격 전체 준수 의무

**유의 사항**

- OKF는 형식 규격이며 언제 어떤 단위로 문서를 만들지는 정하지 않습니다. 모듈화 기준은 따로 정해야 합니다.
- v0.1에서 v0.2로 바뀌며 하위 호환이 깨진 변경이 있었습니다. 도구가 규격 버전에 강하게 묶이지 않게 합니다.
- `index.md`와 `log.md`는 OKF의 예약 파일명입니다.
- OKF의 링크는 일반 Markdown 형식입니다. 노트에는 위키 링크가 266개, Markdown 링크가 39개 있습니다. 제안은 위키 링크를 당분간 유지하는 것이며, 도구는 두 형식을 모두 읽어야 합니다.
- 기존 문서를 한꺼번에 바꾸지 않습니다. `type`이 없는 문서도 계속 정상 처리해야 합니다.
- `generated.by`로 사람과 AI의 작성을 구분합니다(`human:<id>`, `<producer>/<version>`). 직접 쓰기 목표를 확인하는 데 씁니다.

**예시 (합성 데이터)**

```markdown
---
type: 결정
title: 예시 규칙
description: 표시 항목과 그 결정 경위
tags: [예시]
generated: { by: human:example, at: 2026-11-05T10:00:00+09:00 }
sources:
  - id: tl-1
    resource: timeline/daily/2026-09/2026-09-03.md
---

본문은 자유 형식으로 씁니다.
```

## 5. 미결 쟁점

구현 전에 사용자와 논의할 사항입니다.

1. **문서 종류:** 2026-11-05에 결정했습니다(2절 9~14번). 4종이 실제 문서에 맞는지는 파일명으로만 대조했으므로, 쓰면서 검증합니다.
2. **기존 구조의 처리:** 2026-11-05에 결정했습니다(2절 15~17번).
3. **`ai-organize`, `suggest-ai`의 처리:** 2026-11-05에 결정했습니다(2절 18번).
4. **타임라인 기반 제안(리뷰):** 2026-11-05에 결정했습니다(7절). 기존 `memory_tool/review/` 코드는 재사용하지 않고 삭제합니다.
5. **글쓰기 지원 단계:** 2절 12번의 순서를 임시 기본값으로 두고, 써 보면서 조정합니다. 이 순서는 가이드 파일에 적으므로 코드를 바꾸지 않고 수정할 수 있습니다.
6. **모듈 생성 기준:** 2026-11-05에 임시 기준을 정했습니다(7.2절). 써 보면서 조정합니다.
7. **기존 노트의 처리:** 도구 쪽 형식이 정해진 뒤 노트 세션에서 별도로 논의합니다. 쟁점은 `Projects/` 사본(모듈 용량의 42%), 300줄을 넘는 문서 37개, 비어 있는 `PLAN.md` 53개입니다.

## 6. 구현 계획

브랜치는 `feature/module-format-and-ai`입니다. 시작 시점의 테스트는 454개가 모두 통과합니다. 각 단계는 별도의 커밋으로 나누고, 단계마다 테스트를 통과시킵니다.

**버전 1.2.0**

1. **읽기 경로와 파일 구조**
   - `core/timeline.py`로 타임라인 경로 처리를 모읍니다.
   - 모듈 문서 찾기를 `resolve_module_doc`으로 모읍니다. 대상은 예전 파일명을 직접 읽는 파일 중 `memory_agent`, `ai_organizer`, `ai_suggester`, `module_summarizer`, `context/builder`, `warnings`, `health_checker`, `tui/modules_mode`입니다. 사용하지 않는 `notion/`은 제외합니다.
   - `discover_all_modules`가 `PLAN.md`를 제외하게 고칩니다. `"PLAN.md".isupper()`가 거짓이라 지금은 모듈로 나열됩니다.
   - `mmodule rename`이 단일 파일과 하위 문서를 올바로 옮기게 고칩니다. 현재는 `topic.md`, `topic/child/child.md`의 이름을 바꾸면 `subject/topic/child/child.md`가 되고 `topic.md`는 남습니다.
2. **`mask`, `msummary`:** 오류를 고치고, 아래의 회귀 테스트를 합성 데이터로 작성합니다.
3. **제거와 정리**
   - `auto-tag`, `planner/module_plan.py`, `mplan module`을 제거합니다.
   - 도움말의 없는 옵션과 API 키만 안내하는 오류 메시지를 고칩니다.
   - `minit`의 기본 제공자를 사용 가능한 쪽으로 정하게 바꿉니다.
   - `mcontext`가 출력하는 예전 모듈 기준 안내를 고칩니다.
4. **AI 명령**
   - `mmodule audit`을 추가하고 `ai-organize`는 경고를 내는 별칭으로 둡니다. 이동, 계층, 네임스페이스 제안은 제거합니다.
   - `suggest-links --ai`를 추가하고 `suggest-ai`는 별칭으로 둡니다.
5. **새 문서 형식**
   - `mmodule create [--type 종류]`가 frontmatter와 제목만 만들게 합니다. 새 문서는 `주제.md` 하나이며, 하위 문서를 만들 때 2절 17번처럼 동작합니다.
   - `--kind`, `--nature`, `--draft`, `grow`, `merge-templates`는 기존 동작을 유지하되 경고를 출력합니다.
   - `mcheck`가 `sources`의 코드 경로도 검증하게 합니다. `Related Files`, `Decisions`, `Current` 제목은 있으면 읽고 없어도 정상으로 처리합니다.
   - 위키 링크와 Markdown 링크를 모두 읽는지 확인하고, 읽지 못하면 고칩니다.
6. **AI 가이드**
   - 종류별 가이드 4개를 추가합니다. 기존 템플릿의 갱신 계기, 실패 사례, 반대 논거를 질문으로 옮깁니다.
   - `mmodule guide <종류>`와 `mt-write` 스킬을 추가하고, `minit`의 스킬 복사 목록에 넣습니다.
   - `from-text`가 같은 가이드를 읽고 단일 문서로 저장하게 합니다.
7. **플러그인과 문서**

## 7. 리뷰 설계와 구현 계획

2026-11-05에 사용자와 논의하여 정했습니다. 사용자는 기록이 문서로 옮겨지지 않는 원인으로 고르기 어려움, 쓰기 부담, 계기 없음을 모두 꼽았습니다.

### 7.1 구조와 범위

1. **명령:** 옮기기와 돌아보기를 `mreview` 하나로 합칩니다. 돌아보기는 선택 사항입니다.
2. **기존 기능:** `mreview weekly`, `monthly`와 관련 코드를 호환 기간 없이 삭제합니다. 이미 만들어진 리뷰 파일은 그대로 둡니다.
3. **기간:** 기본은 지난 리뷰 이후입니다. 첫 실행은 최근 14일을 읽고, `--since`로 직접 지정할 수 있습니다.
4. **파일:** 리뷰마다 `reviews/YYYY-MM-DD.md`를 하나 만듭니다. 지난 리뷰 시점은 새 형식의 파일에서만 얻으므로 별도의 상태 파일을 두지 않습니다.
5. **알림:** 지난 리뷰 후 7일 이상 지나고 기록이 10건 이상이면, 그날의 첫 `m`과 `mcontext`에서 한 줄로 알립니다. 값은 설정에서 바꾸거나 알림을 끌 수 있습니다.
6. **환경:** 이번 설계에서 Obsidian은 제외합니다.
7. **전송:** 확인 없이 현재 LLM 설정의 제공자로 기록을 보냅니다. 리뷰 전용 제공자는 두지 않습니다.
8. **제안 생성:** `mreview`가 LLM을 직접 호출합니다. 이후의 VS Code 화면을 위해 `--json` 출력을 지원합니다.

### 7.2 옮기기

1. **후보 기준:** 기록을 주제로 묶고, 다음 중 하나에 해당하면 후보로 삼습니다. 기준은 코드가 아니라 파일에 적어 조정할 수 있게 합니다.
   - 나중에 "왜 이렇게 정했지?"에 답해야 하는 결정
   - 다시 찾아볼 가능성이 큰 값, 명령, 절차, 문제 해결 방법
   - 작동 원리를 새로 이해하게 된 내용
2. **제외:** 진행 상황만 적은 기록, 이미 문서에 반영된 내용, 전에 거절한 주제를 뺍니다. 검색 기록이 없으므로 "실제로 다시 찾아본 경우"는 기준에서 뺍니다.
3. **순서:** 기존 문서 갱신을 먼저 제안합니다. 여러 날 반복된 주제는 우선순위를 높이되, 필수 조건으로 두지 않습니다.
4. **새 제안의 선택:** 지금 쓰기, 나중에 쓰기, 거절 중 하나를 고릅니다.
5. **대기 항목의 선택:** 썼음, 계속 대기, 버림, 지금 쓰기 중 하나를 고릅니다.
6. **한도:** 새 제안은 다섯 건까지 받습니다. 대기 항목과 합쳐 남은 항목이 다섯 건을 넘는 동안에는 나중에 쓰기와 계속 대기를 고를 수 없습니다. 다섯 건을 넘는 후보는 건수만 알리고 버립니다.
7. **일시정지:** 진행 상황을 리뷰 파일에 저장하고, 재개할 때 AI를 다시 호출하지 않습니다. 기간은 시작 시점으로 고정하며, 끝내기 전에는 새 리뷰를 시작하지 않습니다.
8. **`audit` 연결:** 후보로 넣지 않습니다. 갱신할 문서가 분할 후보일 때만 참고로 한 줄 알립니다. 이전 계획과 달리 병합 후보는 리뷰에 쓰지 않습니다.
9. **Goal Loop 후보:** 첫 버전에서 뺍니다.

### 7.3 쓰기와 돌아보기

1. **지금 쓰기:** 리뷰를 일시정지하고 그 항목을 씁니다. "썼음"으로 표시할 때까지 남은 항목에 포함합니다.
2. **문서 생성:** 제안을 고를 때가 아니라 쓰기를 시작할 때 파일을 만듭니다. 빈 문서가 쌓이지 않게 하기 위해서입니다.
3. **대기 항목 쓰기:** 다음 리뷰를 기다리지 않고 `mreview write`로 언제든 같은 절차로 시작합니다.
4. **도구 선택:** 매번 설치된 CLI(Claude Code, Codex, Antigravity)와 혼자 쓰기를 메뉴로 보여 주고, 기본값은 Enter로 고릅니다. `--with`로 바로 지정할 수도 있습니다.
5. **맥락 전달:** 스킬을 CLI별로 설치하지 않습니다. 대화형 CLI를 프로젝트에서 실행하고, 절차 파일과 작업 파일을 읽으라는 짧은 지시를 넘깁니다. CLI를 종료하면 `mreview`로 돌아옵니다. `agy`는 `-i`로 지시를 넘깁니다.
6. **돌아보기:** 혼자 쓰기는 고정 질문이 주석으로 적힌 리뷰 파일을 엽니다. 함께 쓰기는 선택한 CLI가 기록을 읽고 대화 중에 묻습니다. 미리 만드는 AI 질문은 없고, 건너뛸 수 있습니다.

### 7.4 구현 중 확인한 사항

- `mreview`는 `pyproject.toml`의 `[project.scripts]`에 없습니다. `cli.py`에 `review_cli`만 있으므로, 패키지를 설치해도 이 명령은 생기지 않습니다. 삭제와 함께 등록합니다.
- 기존 주간 리뷰는 그 주에 기록이 있으면 `NameError`로 중단됩니다. 삭제 대상이므로 고치지 않습니다.
- 지난 리뷰의 끝을 날짜로만 저장하면, 리뷰한 날의 이후 기록이 다음 리뷰에서 빠집니다. 그래서 시각까지 저장합니다. 파일 이름은 날짜로 두되, 같은 날의 두 번째 리뷰는 `YYYY-MM-DD-2.md`로 저장합니다.
- `--date`로 지난 날짜에 추가한 기록은 다음 리뷰 범위에서 빠질 수 있습니다. 첫 버전에서는 감수합니다.
- "이미 문서에 반영된 내용"은 문서 본문을 보내지 않으므로 완전히 걸러 내지 못합니다. AI는 문서 이름과 `description`만 봅니다.

### 7.5 구현 계획

브랜치는 `feature/review`, 버전은 1.3.0입니다. 시작 시점의 테스트는 699개가 모두 통과합니다. 각 단계는 별도의 커밋으로 나누고, 단계마다 테스트를 통과시킵니다. 테스트 데이터는 합성 데이터만 씁니다.

1. **기존 기능 삭제와 명령 등록**
   - `memory_tool/review/`의 기존 파일 세 개와 `commands/timeline.py`의 `review` 명령을 삭제합니다.
   - `commands/review.py`를 추가하고, `pyproject.toml`에 `mreview`를 등록합니다.
2. **리뷰 파일과 상태 규칙(`review/store.py`, `review/collector.py`)**
   - 리뷰 파일의 frontmatter에 기간, 상태(진행 중, 완료), 항목과 항목별 상태를 저장합니다. 본문의 `## 옮기기`는 저장할 때마다 frontmatter에서 다시 쓰고, `## 돌아보기`는 건드리지 않습니다.
   - 지난 리뷰 찾기, 대기 항목 이월, 남은 항목 계산과 미루기 허용 판단을 구현합니다.
   - 기간 내 기록의 수집과 통계는 `core/timeline.py`의 경로 처리를 재사용합니다.
3. **제안 생성(`review/proposer.py`)**
   - 기록, 문서 이름과 `description`, 최근 거절한 주제로 프롬프트를 만들어 `LLMClient`로 호출합니다. 후보 기준은 `templates/guides/`의 파일에 둡니다.
   - 응답의 JSON을 검증합니다. 없는 날짜를 근거로 든 제안과 없는 문서를 갱신 대상으로 삼은 제안은 버립니다.
   - 호출이나 파싱에 실패하면 리뷰 파일을 만들지 않고, 지난 리뷰 시점도 그대로 둡니다.
   - 기록이 150KB를 넘으면 호출하지 않고 `--since`로 기간을 좁히라고 안내합니다. 임시 값입니다.
   - 갱신 대상 문서가 분할 후보이면 `ModuleAnalyzer`로 줄 수와 제목 수를 계산하여 참고 문구를 붙입니다. 임베딩 모델은 불러오지 않습니다.
4. **대화형 흐름(`mreview`, `mreview list`, `mreview done`)**
   - 대기 항목과 새 제안을 차례로 보여 주고, 7.2절의 선택과 한도를 적용합니다.
   - 일시정지와 재개를 구현합니다.
5. **쓰기 연결(`review/writer.py`, `mreview write`)**
   - 메뉴, 기본값, `--with`, 작업 파일 생성, CLI 실행과 복귀를 구현합니다. 기본값은 쓰기 도구 설정, LLM 제공자가 세 CLI 중 하나일 때의 그 CLI, 메뉴의 첫 항목 순서로 정합니다.
   - 권한 확인을 건너뛰는 옵션은 쓰지 않습니다.
   - 대화형 실행은 자동 테스트로 확인할 수 없으므로, 세 CLI 모두 사용자의 터미널에서 직접 시험합니다. 확인할 내용은 실행과 복귀, 지시 전달(한글 경로 포함), `mmodule create`와 문서 수정 권한, 프로젝트 밖의 지식 베이스 접근입니다.
6. **돌아보기:** 고정 질문과 건너뛰기를 구현하고, AI가 따를 돌아보기 절차를 `templates/guides/`에 추가합니다.
7. **알림(`review/notice.py`):** 첫 `m`과 `mcontext`에 연결합니다. 진행 중인 리뷰가 있으면 그 사실을 대신 알립니다. 알림 오류가 기록을 막지 않게 하고, `m`의 속도 변화를 측정합니다.
8. **`--json`과 문서:** `--json` 출력과 비대화형 선택 명령을 추가합니다. `mhelp`, `docs/USER_GUIDE.md`, `README.md`, `guidelines.md`, `CHANGELOG.md`, 버전을 고칩니다.

**회귀 테스트 필수 사례**

- 남은 항목이 다섯 건을 넘으면 나중에 쓰기와 계속 대기를 거부하고, 다섯 건 이하가 되면 허용합니다.
- 지금 쓰기를 고른 항목은 썼음으로 표시할 때까지 남은 항목에 포함합니다.
- 일시정지 후 재개하면 LLM을 호출하지 않고 같은 제안과 선택을 복원합니다. 진행 중인 리뷰가 있으면 새 리뷰를 시작하지 않습니다.
- 리뷰한 날의 이후 기록이 다음 리뷰에 포함되고, 일시정지 중에 남긴 기록도 다음 리뷰에 포함됩니다.
- 지난 리뷰가 없으면 최근 14일만 읽고, `--since`가 이를 대체합니다. 기존 `reviews/weekly/`, `monthly/` 파일은 지난 리뷰로 치지 않습니다.
- LLM 실패와 잘못된 JSON에서 리뷰 파일이 생기지 않습니다. 없는 날짜와 없는 문서를 가리키는 제안은 버립니다.
- 날짜형과 예전 파일명의 타임라인을 모두 읽습니다.
- 제안을 고르는 것만으로는 모듈 파일이 생기지 않습니다.
- 돌아보기에 쓴 글이 상태 저장 후에도 유지됩니다.
- 알림은 두 조건을 모두 만족할 때만, 그날의 첫 기록에서만 나옵니다. 지난 날짜로 추가한 기록에서는 나오지 않고, 알림 오류는 기록을 막지 않습니다.
- 분할 후보 문구는 갱신 대상 문서가 분할 후보일 때만 붙습니다.

**이번 계획에서 하지 않는 것**

- Obsidian 플러그인 변경. 다만 플러그인의 `recordTimeline`이 `m`의 출력을 그대로 돌려받으므로, 알림 문구가 플러그인 화면에 나타날 수 있습니다. 플러그인 작업 때 확인합니다.

## 8. JSON 출력 설계와 구현 계획

2026-11-06에 사용자와 논의하여 정했습니다. 6절 10번의 작업이며, 목적은 11번 VS Code 화면과 이후의 서버 접속이 터미널 출력을 해석하지 않고 CLI를 호출해서 결과를 받게 하는 것입니다.

### 8.1 범위

이름은 "AI 기능의 JSON 출력"이지만, 11번 화면의 첫 버전 후보 중 AI를 쓰는 기능은 리뷰 요청뿐이며 이미 JSON 출력이 있습니다. 화면에 먼저 필요한 기록 조회와 검색은 AI 명령이 아닙니다. 그래서 범위를 넓혔습니다.

| 분류 | 명령 | 지금 상태 |
|---|---|---|
| 기록 | `m` | 없음 |
| 조회 | `mtoday`, `mday`, `mweek`, `mmonth`, `mdays` | 없음 |
| 검색 | `ms` (키워드, 의미, 혼합) | 없음 |
| AI | `msummary`, `mmodule suggest-links --ai`, `mmodule from-text` | 없음 |
| AI | `mask`, `mreview` | 있음. 항목만 추가합니다 |

`mmodule audit`은 이름과 달리 LLM을 부르지 않으므로 이번 범위에서 제외합니다.

### 8.2 공통 관례

기존 `mask --json`, `mreview --json`의 관례를 이어 갑니다.

- 결과는 표준 출력에 JSON 한 줄로 출력합니다. 성공하면 `"ok": true`, 실패하면 `"ok": false`, `"code"`, `"error"`를 담습니다.
- 진행 문구와 "캐시된 결과 사용" 같은 안내는 출력하지 않습니다. 오래 걸리는 AI 명령도 끝에 결과 한 줄만 출력하며, 진행 상황은 화면이 스스로 표시합니다.
- 사람에게 보여 줄 부가 안내는 `notices` 목록에 `{"kind", "message"}`로 담습니다. 문장은 CLI가 `help.language`에 맞춰 만든 것을 그대로 씁니다.
- 실패의 `code`는 화면이 판단하는 기준입니다. `error` 문장은 지금처럼 대부분 영어로 둡니다.
- 기존 `mask`, `mreview`의 JSON에는 `code`와 `notices`만 추가하고 기존 항목은 바꾸지 않습니다. Obsidian 플러그인은 출력에서 JSON으로 읽히는 마지막 줄의 필요한 항목만 읽으므로 영향을 받지 않습니다.

실패 코드의 첫 목록은 다음과 같습니다. 구현하면서 더 필요하면 추가합니다.

| `code` | 뜻 |
|---|---|
| `not_initialized` | 지식 베이스가 없습니다 |
| `invalid_argument` | 날짜, 옵션 등 입력이 잘못되었습니다 |
| `not_found` | 문서나 파일이 없습니다 |
| `future_time` | 미래 시각에 기록하려 했습니다 |
| `distant_past` | 오래된 날짜입니다. `--force`로 기록할 수 있습니다 |
| `llm_unavailable` | 사용할 수 있는 LLM 제공자가 없습니다 |
| `llm_failed` | LLM 호출이나 응답 해석에 실패했습니다 |
| `failed` | 그 밖의 실패입니다 |

### 8.3 기록의 모양

조회와 검색은 기록 한 건을 같은 모양으로 담습니다. `text`는 파일에 적힌 그대로 두고, 태그는 따로 뽑아 `tags`에 넣습니다. 태그 규칙은 `m`이 쓰는 규칙과 같습니다. 즉, 앞에 붙은 `[태그]`와 끝에 붙은 `#태그`를 읽습니다. 이 해석은 `core/timeline.py` 한 곳에 둡니다.

```json
{"date": "2026-11-06", "time": "14:30", "text": "[버그] 로그인 오류 수정", "tags": ["버그"]}
```

### 8.4 명령별 출력

- **조회:** `days` 목록에 날짜마다 `date`, `path`, `entries`, `content`(파일 원문)를 담습니다. 원문을 함께 담는 이유는 `- 시각 | 내용` 형식이 아닌 줄(Obsidian에서 손으로 적은 메모 등)이 화면에서 사라지지 않게 하기 위해서입니다. 응답에는 요청한 기간 `from`, `to`도 담습니다.
- **기간 지정:** `mdays`에 `--from`, `--to`(YYYY-MM-DD)를 추가합니다. 이름은 `ms`의 옵션과 맞춥니다. 기존 다섯 명령에도 `--json`을 추가하며, 모두 같은 출력 형식을 씁니다.
- **기록(`m`):** 저장한 기록의 `entry`, `path`, `notices`를 담습니다. 리뷰 알림과 문서 상태 제안이 `notices`에 들어가며, 맥락 자동 갱신은 안내 없이 동작만 합니다.
- **검색(`ms`):** `query`, `mode`(`keyword`, `semantic`, `hybrid`), `results`를 담습니다. 결과마다 `path`, `kind`(`timeline`, `module` 등), `line`, `text`(찾은 줄), `context`, `score`, `date`를 담고, 타임라인 기록이 걸렸으면 8.3절의 `entry`를 함께 넣습니다.
- **`msummary`:** 범위, 요약 글, 캐시 사용 여부를 담습니다.
- **`suggest-links --ai`:** 후보마다 문서 경로, 이유, 신뢰도를 담습니다.
- **`from-text`:** 저장한 경로, 문서 이름, 종류, 설명을 담습니다. `--preview`이면 저장하지 않고 본문을 담습니다.

### 8.5 구현 중 확인한 사항

- `day` 명령은 도움말과 docstring에 `mday`로 적혀 있지만, `pyproject.toml`에 실행 명령으로 등록되어 있지 않습니다. 이번에 등록합니다.
- `mhelp`는 `mdays`의 기본값을 7일로 안내하지만, 실제 기본값은 14일입니다. 이번에 고칩니다.
- 문서 상태 제안(`check_and_suggest_after_command`)은 문장을 직접 출력합니다. `notices`에 담으려면 문장을 돌려주는 형태로 나눠야 합니다.
- `ms`의 의미 검색은 다른 두 방식과 결과 구조(사전)가 다릅니다. JSON에서는 같은 모양으로 맞춥니다.
- 의미 검색(`core/vector_search.py`의 `_collect_timeline_entries`)에 기존 버그가 두 가지 있습니다. 범위 밖이라 고치지 않았습니다.
  - 한 번 색인한 파일은 바뀌지 않는 한 건너뛰므로, 두 번째 검색부터는 그사이에 바뀐 파일만 검색 대상이 됩니다. `--semantic`과 혼합 검색(이 저장소의 기본값)의 의미 검색 부분이 영향을 받습니다.
  - 날짜를 경로에서 직접 조합하므로 `daily/` 구조에서는 `daily-2026-11` 같은 잘못된 날짜가 나옵니다. JSON 출력은 이 값을 쓰지 않고 `date_from_timeline_path`로 날짜를 다시 구합니다.
- `mhelp today`는 없는 옵션 `--yesterday`를, 사용자 안내서는 없는 옵션 `mtoday --reverse`, `--limit`을 안내했습니다. 이번에 지웠습니다.
- `mmodule` 함수 안에 그래프 내보내기용 지역 변수 `json_output`이 있어서 같은 이름의 모듈을 가렸습니다. `graph_json`으로 바꿨습니다. `mask`, `mreview`의 `--json` 매개변수도 같은 이유로 `as_json`으로 바꿨습니다.
- 지식 베이스를 찾지 못하면 `get_base_path`는 `~/.memory`로 돌아갑니다. 그래서 "지식 베이스 없음" 테스트는 경로 함수를 바꿔 끼워서 작성했습니다.

### 8.6 구현 계획

브랜치는 `feature/json-output`, 버전은 1.4.0입니다. 시작 시점의 테스트는 818개가 모두 통과합니다. 각 단계는 별도의 커밋으로 나누고, 단계마다 테스트를 통과시킵니다. 테스트 데이터는 합성 데이터만 씁니다.

1. **공통 출력과 기록 해석**
   - JSON 출력, 실패 코드, `notices`를 만드는 공통 함수를 `commands/` 아래 한 모듈에 둡니다. `mask`, `mreview`의 출력 함수도 이 모듈을 쓰게 합니다.
   - `core/timeline.py`에 기록 한 줄을 `time`, `text`, `tags`로 나누는 함수와, 기간의 파일을 날짜순으로 읽는 함수를 둡니다. `review/collector.py`도 같은 경로 처리를 씁니다.
2. **조회 명령:** 다섯 명령에 `--json`을 추가하고, `mdays`에 `--from`, `--to`를 추가합니다. `mday`를 등록하고 `mhelp`의 기본값 안내를 고칩니다.
3. **기록 명령:** `m --json`을 추가합니다. 문서 상태 제안을 문장을 돌려주는 함수와 출력하는 함수로 나눕니다.
4. **검색 명령:** 세 방식의 결과를 같은 모양으로 바꾸는 함수를 두고 `ms --json`을 추가합니다.
5. **AI 명령:** `msummary`, `suggest-links --ai`, `from-text`에 `--json`을 추가합니다. `mask`, `mreview`의 실패에 `code`를 붙입니다.
6. **문서:** `mhelp`, `docs/USER_GUIDE.md`, `CHANGELOG.md`를 고치고 버전을 1.4.0으로 올립니다. JSON 형식은 화면을 만들 때 다시 찾아볼 내용이므로 `docs/USER_GUIDE.md`에 한 절로 정리합니다.

**회귀 테스트 필수 사례**

- 모든 `--json` 출력은 한 줄이며 `json.loads`로 읽힙니다. 한글이 그대로 들어가고, 터미널 폭 때문에 줄이 바뀌지 않습니다.
- JSON 모드에서는 진행 문구와 안내 문장이 표준 출력에 섞이지 않습니다.
- 날짜형과 예전 파일명의 타임라인을 모두 읽습니다.
- `[태그]`로 시작하는 기록과 `#태그`로 끝나는 기록에서 태그를 뽑고, `text`는 원문 그대로 둡니다.
- 형식에 맞지 않는 줄은 `entries`에서 빠지지만 `content`에는 남습니다.
- `--from`이 `--to`보다 늦거나 날짜 형식이 틀리면 `invalid_argument`로 실패합니다. 기록이 없는 기간은 실패가 아니라 빈 목록입니다.
- `m --json`은 미래 시각에 `future_time`, 오래된 날짜에 `distant_past`를 돌려주고, 그날의 첫 기록에서 리뷰 알림을 `notices`에 담습니다.
- 검색의 세 방식이 같은 모양을 돌려주고, 타임라인 결과에만 `entry`가 있습니다.
- LLM을 쓸 수 없으면 AI 명령은 `llm_unavailable`로 실패합니다.
- 기존 `mask --json`, `mreview --json`의 항목이 그대로 남아 있습니다.

**이번 계획에서 하지 않는 것**

- 11번 VS Code 화면 자체, 서버 접속, Obsidian 플러그인 변경
- 진행 상황을 줄마다 출력하는 방식(JSON Lines). 필요해지면 나중에 추가하며, 마지막 줄을 결과로 읽는 화면은 그대로 동작합니다.
- `mmodule audit`과 그 밖의 AI가 아닌 명령(`mmodule list` 등)의 JSON 출력

### 8.7 구현 결과

8.6절의 여섯 단계를 모두 커밋했으며, 테스트 869개가 통과합니다. 새 테스트는 `tests/test_json_output.py`에 있고, 모두 합성 데이터입니다. LLM과 의미 검색은 가짜 객체로 바꿔 시험했습니다.

**계획과 달라진 점**

- 실패 코드에 `feature_unavailable`을 추가했습니다. 의미 검색에 필요한 선택 패키지가 없을 때 씁니다.
- `msummary`의 캐시 사용 여부는 요약 모듈을 고치지 않고, LLM 호출 수를 세어 판단합니다(`_CountingClient`).
- `review/collector.py`는 이미 `Timeline.resolve_existing_file`을 쓰고 있어서 고치지 않았습니다.
- 모든 JSON 출력은 표준 출력의 바이트 스트림에 UTF-8로 씁니다. Windows에서 출력을 다른 프로그램으로 넘기면 기본 인코딩이 UTF-8이 아니기 때문입니다.

**남은 일**

- `mday`는 새 실행 명령이므로, 패키지를 다시 설치해야 생깁니다(`pip install -e .`).
- 실제 LLM 제공자로 `msummary --json`, `suggest-links --ai --json`, `from-text --json`을 실행해 보지 않았습니다.
