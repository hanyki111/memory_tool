# 성격별 §2 본문 목차 (5종)

`current.md`의 `## 2. 본문` 자리에 붙여 넣는다. 각 블록의 **필수 요소**는 생략하지 않는다.

`mmodule create --kind knowledge --nature <성격>` 은 이 파일에서 해당 블록을 읽어
자동으로 채운다.

---

## concept (개념) — 서사형

> **갱신 트리거:** 내 이해가 깊어질 때 · **필수:** 비유, 실행 가능한 예제

```markdown
### 2.1 왜 필요한가 (문제 상황)
<!-- 이 개념이 없을 때 무엇이 곤란한가. 개념이 아니라 문제부터 시작한다. -->

### 2.2 핵심 비유
<!-- 실생활에 빗댄 하나의 강한 비유 -->

### 2.3 원리와 구조
<!-- 비유를 걷어낸 실제 메커니즘. 도식·표 사용 -->

### 2.4 예제
<!-- 따라 할 수 있는 최소 예제. 코드 개념이면 실행 가능한 코드 -->

### 2.5 장점과 한계
<!-- 한계를 반드시 함께. 장점만 적힌 개념 설명은 광고다 -->

### 2.6 자주 하는 오해
<!-- 내가 처음에 잘못 이해했던 것. 이 항목이 재학습 비용을 가장 크게 줄인다 -->

### 2.7 인접 개념과의 비교
| 항목 | 이 개념 | 인접 개념 A | 인접 개념 B |
| :--- | :--- | :--- | :--- |
```

## reference (레퍼런스) — 조회형

> **갱신 트리거:** 대상이 패치·개정될 때 · **필수:** 조회표 최상단, 출처, 버전 이력
> **금지:** 서사. 설명 이야기를 섞으면 찾는 시간이 늘어난다. 조회가 목적인 문서다.

```markdown
### 2.0 요약 조회표 (Cheatsheet)
<!-- 가장 자주 찾는 값을 맨 위에. 스크롤 없이 보이는 곳에 둔다 -->
| 항목 | 값 | 비고 |
| :--- | ---: | :--- |

### 2.1 변수 정의
| 기호 | 의미 | 단위 | 범위 |
| :--- | :--- | :--- | :--- |

### 2.2 공식 / 수치 표

### 2.3 예외 · 특수 케이스
<!-- 공식이 적용되지 않는 경우. 실전에서 사고가 나는 지점 -->

### 2.4 측정 방법과 출처
<!-- 필수. 누가 / 언제 / 어떻게 얻은 값인가.
     출처 없는 수치는 패치 한 번에 검증 불가능한 죽은 데이터가 된다 -->
| 데이터 | 출처 | 측정 시점 | 신뢰도 |
| :--- | :--- | :--- | :--- |

### 2.5 버전 이력
<!-- 무효화된 값은 삭제하지 않고 취소선으로 보존 -->
| 버전/패치 | 변경 내용 | 영향받는 섹션 |
| :--- | :--- | :--- |
```

> **갱신 트리거:** 새 증거가 나올 때 · **필수:** 사실/해석 물리적 분리, Red Team

```markdown
### 2.1 Key Findings & Facts (검증된 사실)
<!-- 사실과 해석을 물리적으로 분리한다. 여기에는 수치·직접인용·날짜만.
     "역대 최대" 같은 수식은 사실이 아니라 프레이밍이다 -->

### 2.2 해석과 논증
<!-- 위 사실에서 무엇을 읽어내는가. 추론 단계를 생략하지 않는다 -->

### 2.3 Critical Analysis ([Red Team])
<!-- 필수. 이 판단이 틀리는 조건, 반대 논거, 내가 놓쳤을 변수.
     판단을 담는 문서는 그 판단의 파훼 조건을 함께 적어야 한다 -->

### 2.4 Impact (나에게 무엇을 의미하는가)
<!-- 판단이 행동으로 번역되지 않으면 분석은 감상이다 -->
```

## tracker (추적) — 운영형

> **갱신 트리거:** 시간이 흐를 때 · **필수:** 만료 규칙, 빗나간 예측 보존
> **핵심:** 삭제하지 않는 것이 이 성격의 가치 원천이다. 최신화하며 지우면 자산이 사라진다.

```markdown
> **만료 규칙:** 발동·만료된 항목은 삭제하지 않고 `~~취소선~~ + ✅결과` 로 보존한다.

### 2.1 현황 스냅샷 (YYYY-MM-DD 기준)
<!-- 지금 이 순간의 상태. 날짜 없는 스냅샷은 스냅샷이 아니다 -->

### 2.2 시나리오 매트릭스
| 시나리오 | 확률 | 발동 조건 | 대응 |
| :--- | ---: | :--- | :--- |

### 2.3 이벤트 캘린더
| 일정 | 이벤트 | 관찰 포인트 | 상태 |
| :--- | :--- | :--- | :--- |
<!-- 상태: ⏳ 진행 중 / ✅ 종료 / 🔴 임박 -->

### 2.4 트리거 · 액션
| 조건 | 행동 | 현황 |
| :--- | :--- | :--- |

### 2.5 예측 로그 & 학습된 오류 패턴
<!-- 이 섹션이 tracker의 존재 이유다.
     빗나간 예측을 보존했기 때문에만 오류 패턴을 추출할 수 있다 -->
1. **[오류 패턴 이름]:** 무엇을 어떻게 잘못 예측했는가 → 교훈
```

## method (방법론) — 절차형

> **갱신 트리거:** 적용 피드백이 올 때 · **필수:** 적용 전제, 방법론↔적용 분리
> **원칙:** 재사용 가능한 절차는 방법론 모듈에, 프로젝트별 실제 상수는 적용 모듈에 둔다.
> 섞으면 다음 프로젝트에서 꺼내 쓸 수 없다.

```markdown
### 2.1 적용 전제 (유효 조건 / 무효 조건)
<!-- 필수. 이 절차가 통하지 않는 상황을 먼저 밝힌다 -->

### 2.2 절차
<!-- 단계별. 각 단계의 입력·출력·판정 기준을 명시 -->
1. 
2.

<!-- 이 절차를 돌리면 무엇이 나오는가. 실제 템플릿 -->

### 2.4 체크리스트
- [ ] 

### 2.5 실패 모드 (Pre-mortem)

### 2.6 적용 사례
```
